1. PROJECT OVERVIEW
================================================================================

The Brevitest Acuity Sample Processing Unit (SPU) is an IoT medical diagnostic
device that runs immunoassay tests using:
  - Stepper motor stage for cartridge positioning
  - 3x AS7341 spectrophotometers (via PCA9536 I2C multiplexer)
  - 3x laser diodes (A, B, C channels)
  - Heater with PID temperature control and thermistor
  - Barcode scanner for cartridge identification
  - Piezo buzzer for user alerts
  - RGB LED for status indication

The legacy firmware was a single 5,843-line .ino file plus headers running on
Particle Boron (NRF52840) using Particle Cloud and CouchDB.

The rewrite targets Particle M-SoM (RTL8722DM) with Supabase PostgreSQL backend,
decomposed into 29 source files across clean modules.

Final binary size: Flash 69,854 / RAM 53,634 bytes (msom 6.3.4).

4. METHODOLOGY: THE RALPH LOOP
================================================================================

Every implementation follows the Ralph Loop:

  READ -> DOCUMENT -> IMPLEMENT -> VERIFY -> COMMIT

Step 1: READ LEGACY
  - Find the corresponding function/section in the legacy firmware
  - Note the exact line numbers for reference
  - Understand the behavior, edge cases, timing, and constants
  - Look for #define constants that affect the behavior

Step 2: DOCUMENT
  - Write the user story acceptance criteria
  - Note the legacy reference (file:lines)
  - Document expected inputs, outputs, and side effects

Step 3: IMPLEMENT
  - Write the new code in the appropriate module
  - Preserve exact behavioral compatibility where possible
  - Use the same constants (copy from legacy header)
  - Add appropriate logging (Log.info/warn/error)

Step 4: VERIFY
  - Compile: particle compile msom supabase-firmware --target 6.3.4
  - Run host tests if applicable (g++ test_host.cpp)
  - Check flash/RAM usage (must fit in device memory)
  - Flash to device if hardware testing needed

Step 5: COMMIT
  - Stage specific files (not git add -A)
  - Write descriptive commit message
  - Push to branch

### PRD-Driven Development
Each terminal works from a Product Requirements Document (PRD) in JSON format.
PRDs contain user stories with:
  - Story ID (e.g., ALPHA-001)
  - Title and description
  - Acceptance criteria (testable conditions)
  - Legacy reference (file and line numbers)
  - Dependencies on other stories

### Step 0.5: Document hardware_loop() Behavior
THIS IS THE MOST IMPORTANT FUNCTION IN THE FIRMWARE.
It runs EVERY loop() iteration and handles:
  1. Heater temperature monitoring (updates heater_ready flag)
  2. Cartridge detector debouncing (10ms)
  3. Cartridge insertion handling (reset stage, move to test start, scan)
  4. Cartridge removal handling (reset stage, clear state, idle)
  5. LED/buzzer indicator updates (set_device_indicators)
  6. PID temperature control (heaterController.update())
  7. Buzzer trigger processing

KEY LESSON: The first version of the rewrite was non-functional because
hardware_loop() was missing entirely. Without it, the heater never heats,
cartridges are never detected, and LEDs never update.

### Step 0.6: Document LED Indicator Logic
| State                           | LED Color | Pattern | Buzzer         |
|---------------------------------|-----------|---------|----------------|
| Active operation (test, scan)   | Red       | Solid   | None           |
| Error + invalid cartridge       | Green     | Blink   | Problem (620Hz)|
| Error (other)                   | Red       | Solid   | None           |
| Heating (waiting for temp)      | Red       | Solid   | None           |
| Idle + cartridge + uploaded     | Green     | Blink   | Alert (850Hz)  |
| Idle + cartridge (no upload)    | Green     | Blink   | None           |
| Idle + no cartridge + ready     | Green     | Solid   | None           |
| Idle + no cartridge + heating   | Red       | Solid   | None           |
| Uploading results               | Red       | Solid   | Alert if cart  |
| Initializing                    | Red       | Solid   | None           |

  DataTypes.cpp      - CRC32, Base64, serialization, string conversions

### Key Implementation Notes

ALPHA-001 to ALPHA-003: Enums
  - DeviceMode enum must match legacy values EXACTLY (for cloud compatibility)
  - TestState, CartridgeState, ErrorCode enums
  - String conversion functions for every enum value

ALPHA-004: State Transition Validation
  - Hard-coded valid transitions (canTransitionTo matrix)
  - ALWAYS allow transition to ERROR_STATE from any state
  - ALWAYS allow transition to IDLE from any state (reset path)
  - Same-state transitions are INVALID

ALPHA-005: History Logging
  - 50-entry circular buffer for state transitions
  - Records: from_mode, to_mode, timestamp, trigger string
  - Essential for debugging state machine issues

ALPHA-009: Heater Debouncing
  - heater_ready flag: temp within 1.0C of target AND temp below target
  - 5000ms debounce prevents false positives
  - CRITICAL: Without this, cartridges can be damaged by premature insertion

ALPHA-010: Device Indicators (set_device_indicators)
  - Must match legacy LED behavior exactly (users know red=wait, green=go)
  - Called every loop iteration from hardware_loop()

ALPHA-011: hardware_loop()
  - THE HEART OF THE FIRMWARE
  - Must run every loop() iteration
  - Handles all real-time hardware monitoring and debouncing

ALPHA-012: Main Loop Integration
  - loop() calls: processSerialCommands() + hardware_loop()
  - State-driven behavior with switch statement
  - Timeout handling for all cloud operations

### Pin Mapping (M-SoM)
  HEATER = D4, THERMISTOR = A6
  LASER_A = D5, LASER_B = D6, LASER_C = D7
  MOTOR_STEP = D13, MOTOR_DIR = D8, MOTOR_SLEEP = D12
  BARCODE_TRIGGER = D23, BARCODE_READY = D22
  STAGE_LIMIT = D26, CARTRIDGE_DETECT = D3
  LED_DATA = D2, BUZZER = A0
  I2C: SDA = D0, SCL = D1

### Key Implementation Notes

HAL Layer Design:
  - Static namespace (not a class) for zero-overhead hardware access
  - All pin initialization in HAL::init()
  - Thermistor uses 21-point lookup table with linear interpolation
  - Temperature returned in 10x Celsius format (375 = 37.5C)

HeaterController:
  - PID uses INTEGER MATH (no floating point on embedded)
  - Kp=80/4, Ki=1/50000, Kd=1/5 (numerator/denominator pairs)
  - Failsafe: max continuous on-time of 2000ms
  - Over-temperature cutoff at 60.0C
  - Thermal runaway detection

MotorController:
  - 1/8 microstepping: 25 microns per step
  - Home to limit switch before any absolute positioning
  - Wake delay: 10ms (A5985GETTR-T datasheet requirement)
  - Sleep motor after positioning to save power

Spectrophotometer:
  - PCA9536 I2C multiplexer at 0x41 selects channel A/B/C
  - AS7341 at 0x39 reads 10 spectral channels (F1-F8, Clear, NIR)
  - Baseline capture required before test scans
  - SMUX configuration for channel mapping

LaserController:
  - Safety interlock: requires cartridge present to enable
  - Maximum continuous on-time: 30 seconds
  - Pulse mode: 20us on, 2ms cycle (configurable)

9. PHASE 4: CLOUD PROTOCOL AND STORAGE (Gamma - 16 stories)
================================================================================

### Files Created
  CloudProtocol.cpp/h  - JSON serialization/deserialization
  SupabaseClient.cpp/h - HTTPS client for Supabase Edge Functions
  StorageManager.cpp/h - EEPROM + LittleFS filesystem

### Cloud Endpoints (4 total)
  1. validate-cartridge - Verify cartridge UUID, get associated assay
  2. load-assay         - Download BCODE instructions for test
  3. upload-test        - Upload test results (9668-byte record)
  4. reset-cartridge    - Reset cartridge state for re-testing

### JSON Serialization
  - Manual sprintf-based serialization (no JSON library)
  - Manual strstr-based deserialization (findJsonString, findJsonInt, etc.)
  - Request ID: UUID v4 format for correlation
  - All timestamps as uint32_t (Unix epoch)

### Storage Architecture
  EEPROM:
    - Device configuration (WiFi, firmware version, data format)
    - Recovery data (running test UUID for crash recovery)
    - Stress test cycle counters

  LittleFS Filesystem:
    /cache/     - Failed upload test records (max 50 files, FIFO eviction)
    /assay/     - Downloaded assay instructions (max 50 files)
    /validation/ - Magnetometer validation data
    /buffer/    - Temporary working storage

### Key Implementation Notes
  - Retry logic: 3 attempts with 5s exponential backoff
  - Failed uploads cached to filesystem for later retry
  - Interrupted test recovery on startup (checks EEPROM for in-progress test)
  - CRC32 checksums on all test records (IEEE 802.3 with lookup table)
  - Static assertions verify struct sizes at compile time

### IMPORTANT: CloudProtocol.cpp Extraction
  Originally, the serialization functions were implemented inside
  SupabaseClient.cpp but declared in CloudProtocol.h. This was refactored
  to move all serialize/deserialize functions into CloudProtocol.cpp where
  they belong. This allows host-side testing without pulling in the full
  SupabaseClient (which depends on Particle HTTP libraries).

10. PHASE 5: SERIAL COMMANDS AND TEST ENGINE (Delta - 28 stories)
================================================================================

### Files Created
  CommandParser.cpp/h    - Serial line parsing (comma-delimited integers)
  SerialCommands.cpp/h   - 100+ command handlers
  BCODEInterpreter.cpp/h - Custom instruction interpreter
  TestRunner.cpp/h       - Test execution orchestrator

### Serial Command Format
  Input: "command_id" or "command_id,param1,param2,..."
  Response: "OK:value" or "ERR:code:message"
  Baud rate: 115200

### Command Categories (100+ commands)
  1-9      System (reset, EEPROM, pins)
  10-12    Serial messaging control
  20-29    Stage motion (home, move, oscillate)
  30-33    Laser control (A, B, C, all)
  40-43    Buzzer control (tone, alert, problem)
  50-55    Heater (temperature, PID, target)
  60       Barcode scanner trigger
  70-73    Magnetometer validation
  90-93    Stress testing
  301-311  Spectrophotometer (params, channels, scans)
  400-406  Cloud operations (cache, upload, assays)
  8000-8999 Radio control (WiFi, cellular, BLE, FCC)
  9000-9020 State management (view, force, history)

### BCODE Interpreter
  Custom instruction set for controlling test execution.
  Format: "opcode:param1,param2|opcode:param1|..."
  Delimiters: | (instruction), : (opcode/params), , (params), # (end)

  Opcodes:
    0  START_TEST      - Begin test sequence
    1  DELAY(ms)       - Delay with callback for heater control
    2  MOVE_MICRONS(microns, step_delay)
    3  OSCILLATE(microns, step_delay, cycles)
    10 SET_SENSOR_PARAMS(gain, astep, atime)
    11 BASELINE_SCANS(num_scans)
    14 TEST_SCANS(num_scans)
    15 SENSOR_READING(channel, gain, astep, atime)
    16 CONTINUOUS_SCANS(baseline, start, distance, step_delay)
    20 REPEAT_BEGIN(iterations)  - Start repeat block (4 levels nesting)
    21 REPEAT_END               - End repeat block
    99 END_TEST                 - Complete test

  Callback-based hardware integration:
    - StageMoveCallback, StageOscillateCallback
    - SpectroConfigCallback, SpectroScanCallback
    - DelayLoopCallback (returns false to cancel)

### TestRunner
  Orchestrates complete test lifecycle:
    1. Load assay (BCODE + metadata)
    2. Wait for heater ready
    3. Execute BCODE instructions via BCODEInterpreter
    4. Collect spectrophotometer readings
    5. Finalize record with checksum
    6. Hand off to cloud for upload
  Also supports stress testing (automated repeated cycles).

11. PHASE 6: MAIN LOOP INTEGRATION
================================================================================

### main.ino Structure (the glue)

setup():
  1. Wait for serial (15s timeout)
  2. Initialize HAL (all GPIO pins)
  3. Initialize StorageManager (EEPROM + filesystem)
  4. Check for interrupted test recovery
  5. Initialize HeaterController, start PID
  6. Initialize SerialCommands
  7. Initialize MotorController, home stage
  8. Register Particle.variable (temperature, magnet_validation)
  9. Register Particle.function (runTest, resetDevice, setHeaterTarget, getStatus)
  10. Set initial LED (red solid = initializing)
  11. Transition to IDLE state

loop():
  1. serialCommands.process()
  2. hardware_loop()    <-- CRITICAL: runs every iteration
  3. State-driven switch:
     - VALIDATING_CARTRIDGE: timeout/retry handling
     - LOADING_ASSAY: timeout handling
     - RUNNING_TEST: testRunner.update()
     - UPLOADING_RESULTS: timeout + cache on failure
     - HEATING: check heater_ready, handle pending barcodes
     - BARCODE_SCANNING: trigger scan, route by type
     - etc.

hardware_loop():
  1. Update heater_ready flag from current temperature
  2. Debounce cartridge detector (10ms)
  3. Handle cartridge insertion (reset stage, move to test start, scan)
  4. Handle cartridge removal (reset stage, clear state, idle)
  5. set_device_indicators() for LED/buzzer
  6. heaterController.update() for PID control
  7. BuzzerController::update() for non-blocking tones
  8. laserController.update() for safety interlock

### Cloud Function Handlers (remote control via Particle Cloud)
  runTest(args)       - Start test with cartridge UUID
  resetDevice(args)   - Reset device to IDLE
  setHeaterTarget(args) - Set target temperature
  getStatus(args)     - Return JSON status

12. PHASE 7: FIRMWARE AUDIT
================================================================================

After all 81 stories complete, perform a comprehensive audit.

### Audit Categories
1. TIMING CONSTANTS: Compare every constant to legacy (68 checked, 5 fixed)
2. STATE TRANSITIONS: Verify every valid/invalid transition (26 checked)
3. HARDWARE DRIVERS: Verify against component datasheets (7 drivers)
4. DEAD CODE: Identify unused functions, variables, includes (~150 items)

### Critical Fixes Found During Audit (8 stories: AUD-001 to AUD-008)

AUD-001: LaserController::update() was not being called in hardware_loop()
  - Without this, laser safety interlock (30s max on-time) doesn't work
  - Fix: Added laserController.update() to hardware_loop()

AUD-002: Barcode type routing was incomplete
  - Legacy routes CARTRIDGE/MAGNETOMETER/STRESS_TEST/OPTICAL/SHIPPING
  - New code only handled CARTRIDGE
  - Fix: Added routing for all barcode types in BARCODE_SCANNING handler

AUD-003: Motor wake delay was 1ms, should be 10ms
  - A5985GETTR-T datasheet specifies 10ms wake time
  - Fix: Changed delay in HAL::motorWake() from 1ms to 10ms

AUD-004: AS7341 interrupt not being cleared after read
  - Can cause phantom interrupts and stale data
  - Fix: Added write-1-to-clear after STATUS_1 register read

AUD-005: StorageManager checksum comparison used broken absolute-value logic
  - Was: if (abs(a - b) == 0) which can overflow for uint32_t
  - Fix: Direct uint32_t equality comparison

AUD-006: Duplicate #defines in main.ino shadowing HardwareConfig.h
  - 14 constants duplicated between files
  - Fix: Removed all duplicates from main.ino

AUD-007: TestRunner::stopTest() had identical if/else branches
  - Both branches did the same thing
  - Fix: Collapsed to single code path

AUD-008: Upload timeout didn't cache test data
  - On upload timeout, test data was lost
  - Fix: Added storageManager.cacheTestData() on timeout

### BUG FOUND BY TESTS: BCODE Parameter Parsing
The host tests immediately caught a critical bug in BCODEInterpreter:
  parseInstruction() did not skip past the ':' (ATTR_DELIM) between the
  opcode and parameters. This meant ALL parameterized instructions (MOVE,
  DELAY, SCANS, REPEAT, etc.) would fail with 0 parameters.

  Fix (BCODEInterpreter.cpp, parseInstruction):
    Added: Skip ATTR_DELIM before parameter parsing loop
    Removed: ATTR_DELIM check from parameter loop condition

  This bug would have caused every test to fail on real hardware.
  The host tests caught it before the first flash.

16. ARCHITECTURE DECISIONS AND RATIONALE
================================================================================

### Why Decompose Into 29 Files?
  Legacy: 1 giant .ino file (5843 lines) + 1 header + 1 driver
  New: 29 files averaging ~300 lines each
  Rationale:
    - Each module is independently testable
    - Clear ownership and responsibility
    - Parallel development by multiple terminals
    - Easier to audit and review

### Why Manual JSON Parsing (No Library)?
  - Embedded systems have limited RAM (53KB)
  - ArduinoJson would add ~5KB flash + dynamic allocation
  - Our JSON is simple and predictable (known field names)
  - sprintf/strstr approach is zero-allocation

### Why Integer PID (No Floating Point)?
  - ARM Cortex-M has no hardware FPU on all variants
  - Integer math is 10-100x faster on some Particle platforms
  - PID uses numerator/denominator pairs: Kp = 80/4 = 20.0

### Why Callback-Based BCODE Execution?
  - BCODE interpreter doesn't know about hardware
  - Hardware callbacks are registered by main.ino
  - Interpreter is pure logic, testable without hardware
  - Same callbacks can be mocked for host testing

### Why Static Namespace for HAL?
  - Zero overhead (no object allocation)
  - Clear separation: HAL::readThermistor() vs heater.getTemp()
  - Pin configurations are fixed at compile time
  - No inheritance or polymorphism needed

### Why tests_excluded/ Instead of test/?
  - Particle cloud compile includes ALL files in project directory
  - test/ files would be compiled for device (fail: no desktop headers)
  - tests_excluded/ naming convention prevents inclusion
  - Host tests compile separately with g++ on desktop

17. BUGS FOUND AND FIXED
================================================================================

### Bug 1: Missing hardware_loop() (Pre-audit)
  Severity: CRITICAL (device non-functional)
  Cause: hardware_loop() was not implemented in initial rewrite
  Effect: No heater control, no cartridge detection, no LED updates
  Fix: Implemented hardware_loop() matching legacy line-by-line

### Bug 2: BCODE Parameter Parsing (Found by host tests)
  Severity: CRITICAL (all tests would fail)
  Cause: parseInstruction() didn't skip ':' before parsing params
  Effect: MOVE, DELAY, SCANS, REPEAT all fail with 0 parameters
  Fix: Added ATTR_DELIM skip before parameter loop
  File: BCODEInterpreter.cpp:331-337

### Bug 3: Motor Wake Delay Too Short (Audit AUD-003)
  Severity: HIGH (intermittent motor failures)
  Cause: 1ms delay instead of 10ms per A5985GETTR-T datasheet
  Fix: HAL.cpp motorWake() delay changed to 10ms

### Bug 4: Laser Safety Interlock Not Running (Audit AUD-001)
  Severity: HIGH (laser could stay on indefinitely)
  Cause: laserController.update() not called in hardware_loop()
  Fix: Added to hardware_loop()

### Bug 5: Upload Timeout Data Loss (Audit AUD-008)
  Severity: HIGH (test results lost on network failure)
  Cause: Upload timeout didn't cache data before giving up
  Fix: Added storageManager.cacheTestData() on timeout

### Bug 6: AS7341 Interrupt Not Cleared (Audit AUD-004)
  Severity: MEDIUM (stale readings possible)
  Cause: STATUS_1 register read without write-1-to-clear
  Fix: Added clear after read in AS7341 driver

### Bug 7: Checksum Comparison Overflow (Audit AUD-005)
  Severity: MEDIUM (false checksum mismatches)
  Cause: abs(uint32_t - uint32_t) can overflow
  Fix: Direct equality comparison

### Bug 8: Barcode Type Routing Incomplete (Audit AUD-002)
  Severity: MEDIUM (magnetometer/stress test barcodes ignored)
  Cause: Only CARTRIDGE type was handled
  Fix: Added routing for all 5 barcode types

### Bug 9: Duplicate #defines (Audit AUD-006)
  Severity: LOW (worked but maintenance hazard)
  Cause: 14 constants in main.ino shadowing HardwareConfig.h
  Fix: Removed duplicates

20. LESSONS LEARNED
================================================================================

### Critical Lessons

1. HARDWARE_LOOP IS EVERYTHING
   The single most important function in embedded firmware is the main
   hardware monitoring loop. Without it, the device is a brick. It must:
   - Run every loop() iteration (no delays that block it)
   - Handle all real-time monitoring (temperature, switches, sensors)
   - Update all user-facing indicators (LEDs, buzzer)
   This was the #1 reason the first rewrite attempt didn't work.

2. HOST TESTS CATCH REAL BUGS
   The BCODE parameter parsing bug would have caused every test to fail
   on hardware. Host-side testing found it in seconds, saving hours of
   on-device debugging. Always test pure logic modules on desktop first.

3. COPY CONSTANTS EXACTLY
   Don't "improve" legacy constants. If the heater debounce was 5000ms
   in legacy, it's 5000ms in the rewrite. These values were tuned on
   real hardware over years. Change them only with hardware testing.

4. MOCK PARTICLE.H APPROACH WORKS
   For modules that use Log.info(), millis(), delay(), Wire, Serial:
   Create a mock Particle.h with stub implementations. Use -I. flag
   to override the real Particle.h. This lets you compile firmware
   logic modules on desktop without any Particle SDK.

5. AUDIT AFTER IMPLEMENTATION
   Even after all stories pass, perform a dedicated audit phase.
   We found 8 critical/high bugs that passed all acceptance criteria
   but would have caused real-world failures.

6. EXTRACT SERIALIZATION FROM CLIENT
   Keep JSON serialization in a separate file from the HTTP client.
   This allows host-side testing of serialization without pulling in
   network dependencies.

### Process Lessons

7. PRD-DRIVEN DEVELOPMENT SCALES
   Breaking 81 stories across 4 terminals with JSON PRDs worked well.
   Each terminal had clear scope and minimal merge conflicts.

8. RALPH LOOP PREVENTS DRIFT
   Always reading legacy BEFORE implementing prevents "I think it
   should work like this" guessing. The legacy code IS the spec.

9. STATIC_ASSERT FOR DATA COMPATIBILITY
   static_assert(sizeof(BrevitestTestRecord) == 9668) catches
   struct layout changes at compile time. Essential for binary
   protocol compatibility.

10. GIT COMMIT AFTER EACH PHASE
    Don't accumulate changes. Commit after each story or small group.
    This makes it easy to bisect if something breaks.

### Tooling Lessons

11. MINGW PATH ISSUE ON WINDOWS
    g++ compiles may fail silently (exit code 1, no output) if
    MinGW's bin directory is not in PATH. The compiler executable
    works, but cc1plus.exe can't find its DLLs. Fix:
    export PATH="/c/ProgramData/mingw64/mingw64/bin:$PATH"

12. PARTICLE CLOUD COMPILE INCLUDES EVERYTHING
    The Particle cloud compiler includes ALL files in the project
    directory. Put test files in tests_excluded/ (not test/) to
    prevent them from being compiled for the device target.

13. OTA FLASH REQUIRES DEVICE ONLINE
    particle flash <device-id> only works if the device is connected
    to Particle Cloud. For offline devices, use USB:
    particle flash --serial supabase-firmware.bin
